# Codex Monitor — Final P0 Revalidation Report

Phase: 0E — Sol / High — Final Revalidation Review  
Decision date: 2026-08-10  
Runtime under test: standalone Codex CLI `0.147.0`  
Primary evidence: `P0_REPORT_REVALIDATION_V2_DRAFT.md`, `PHASE_0D1_REPORT.md`, `P0_EVIDENCE_20260810_0D1/`  
Final decision: **NO-GO —不得进入 Phase 1。**

## Executive conclusion

Phase 0D.1 removed the earlier environment blocker. The standalone CLI, managed daemon, owner-only control socket, Unix-socket WebSocket Upgrade, `initialize` / `initialized`, and four read requests all worked. This is real transport evidence.

The product hard gate still fails. The secondary Probe did not receive or correlate any Desktop-created `thread/status/changed`, `turn/started`, item-lifecycle, `thread/tokenUsage/updated`, approval, or `turn/completed` event. Reconnect proved only that the Probe could reconnect, initialize again, and repeat account/thread-list snapshots; it did not prove Desktop Thread reconciliation or missed-event recovery.

The last technical question does not change the decision:

- The Probe **did omit part of the stable read-only reconciliation path**: it called `thread/loaded/list`, but did not call `thread/list`, use discovered in-memory identities with `thread/read(includeTurns: true)`, or compare before/after snapshots.
- That omission makes Phase 0D.1 insufficient to prove the broad proposition “cross-client observation is inherently unsupported.” It may have missed snapshot-visible Thread/status/history information.
- It does **not** explain the missing push events as a skipped official subscription step. The generated stable `0.147.0` client schema contains `thread/unsubscribe` but no `thread/subscribe`. `thread/read` is read-only and explicitly does not subscribe. `thread/list` and `thread/loaded/list` are discovery/snapshot methods, not event attachment methods.
- `thread/resume` can load or rejoin a Thread and is the only stable existing-Thread operation in this schema that plausibly establishes event ownership. It is a conversation-lifecycle operation, exposes configuration overrides, and exists so later turns can append to that Thread. It is prohibited as a substitute for passive observation.

Therefore the evidence supports a narrower but decisive statement: **the tested secondary connection did not receive Desktop-created Turn events, and the installed stable schema exposes no permitted, purely observational method to subscribe that connection to an existing Desktop Thread.** The absolute implementation cause remains unproved, but there is no evidence-backed stable path that can satisfy the frozen runtime-observer requirement. A CONDITIONAL GO would relax a hard gate and is not allowed.

## Stable subscription and reconciliation audit

Authoritative version-specific source: the schema generated by standalone CLI `0.147.0` without `--experimental`, archived under `P0_EVIDENCE_20260810_0D1/schema/`.

| Method / behavior | Stable `0.147.0` schema | Pure observation | Establishes event subscription | Phase 0D.1 execution | Decision |
|---|---:|---:|---:|---:|---|
| `thread/loaded/list` | Yes | Yes | No evidence that it does | Yes | Returned only a response shape in retained evidence; counts/identities were discarded. |
| `thread/list` | Yes | Yes | No | No | Suitable for stored-Thread discovery and snapshot reconciliation, not event attachment. |
| `thread/read` | Yes | Yes | **No** | No | Suitable for summary/history snapshot; official docs explicitly distinguish it from subscribing. |
| `thread/unsubscribe` | Yes | Yes | Removes an existing subscription only | No | Its presence does not imply an unexposed inverse operation may be assumed. |
| `thread/subscribe` | **No** | N/A | N/A | No | Absent from TypeScript and JSON `ClientRequest` unions. There is no official stable passive attach method in the installed schema. |
| `thread/resume` | Yes | **No for this product** | Rejoins/loads a Thread | Prohibited / not run | Lifecycle ownership cannot be used to manufacture observer evidence. |
| `thread/turns/list` / `thread/items/list` | Not in the archived stable request union | Read-oriented | No | No | Current public docs label these experimental; they cannot repair this stable-only P0 and do not provide live subscription. |

The current official [Codex App Server documentation](https://developers.openai.com/codex/app-server) aligns with the version-specific finding: `thread/read` reads without resuming or subscribing, while `thread/start` automatically subscribes the creating client and `thread/unsubscribe` removes a connection's subscription. It documents no `thread/subscribe` request. It also marks the app-server command and WebSocket transport experimental and unsupported for production workloads; the successful local control-socket test is not a production-maturity guarantee.

### What a complete read-only reconciliation probe could have established

A better stable-only probe could have retained only privacy-safe counts and ephemeral in-memory identities, then performed:

1. `thread/loaded/list` to discover current in-memory Thread IDs;
2. `thread/list` with an explicit complete `sourceKinds` set to avoid relying on its interactive-source default, discovering persisted Thread summaries and runtime status;
3. `thread/read(includeTurns: true)` before and after a Desktop Turn;
4. disconnect/reconnect, repeat all three snapshots, and compare a sanitized correlation digest.

That would test coarse status/history reconciliation. It would **not** establish live `turn/*` or `item/*` delivery, lossless in-flight correlation, passive approval routing, or authoritative event recovery. Running that extra probe now is outside Phase 0E's review-only scope and cannot retroactively make P0-B pass.

## Evidence audit

Accepted:

- The official standalone installation resolved to Codex CLI `0.147.0`.
- `remote-control start` created the managed owner-only control socket; the external remote-control connection reported an error, but the local socket remained reachable.
- The Probe completed WebSocket Upgrade, initialize/initialized, and live `account/read`, `account/rateLimits/read`, `account/usage/read`, and `thread/loaded/list` calls.
- Three retained Desktop observer windows (45 s, 45 s, and 20 s) contain initialization/read responses and `remoteControl/status/changed`, but no Thread/Turn/Item event family.
- The reconnect capture proves a new socket connection, new initialize lifecycle, and fresh read responses.
- The archive contains 927 generated schema files and the five P0Probe unit tests pass.
- No credential extraction, private backend, direct JSONL tailing, UI scraping, approval response, account mutation, reset-credit consumption, Probe-created/resumed Turn, or Desktop task mutation was used.

Limitations:

- Sanitization intentionally discarded Thread counts and identities, so the `thread/loaded/list` response cannot prove that the Desktop test Thread was visible to the Probe.
- The Probe did not call `thread/list` or `thread/read`; therefore snapshot reconciliation and Desktop-thread discovery were not completed.
- No event identity exists to correlate a Thread, Turn, and Item.
- No passive approval exercise was run after P0-B failed.
- No account-change, account-switch, token-event, rate-limit update, reset-credit, sleep/wake, or event-race test was completed.
- Negative passive-window evidence does not reveal whether the cause is connection-scoped subscriptions, Desktop/daemon topology, source filtering, or another delivery rule. It only establishes the observed failure and absence of a permitted stable subscription remedy.

## Required product decisions

- Do not implement or ship real-time monitoring of existing Desktop-created Turns from the current architecture.
- Remove/disable yellow `WAITING_APPROVAL` and approval notifications. Never infer approval from active duration, silence, or status polling.
- Do not show Session Token data until authoritative Desktop-thread token events and correlation pass.
- Account may be shown only at the verified response level. Rate limits and Usage remain PARTIAL; hide unsupported fields and all cost estimates, and do not infer quota from tokens.
- Keep active multi-account switching out of scope.
- Do not use `thread/resume`, `thread/start`, or `thread/fork` merely to obtain event ownership.
- Do not substitute private APIs, credential extraction, screen/accessibility scraping, continuous direct JSONL tailing, or a Monitor-owned task lifecycle for the failed observer gate.

## Acceptable architecture redesign directions

### Priority 1 — Obtain a first-party stable observer/broadcast contract

1. **Preserve core experience:** Yes, potentially fully. A documented Desktop observer API, stable subscribe-only method, or first-party Desktop hook that broadcasts Thread/Turn/Item/approval events could preserve “monitor existing Codex Desktop.”
2. **Functions to delete/change:** Until that contract exists, remove all real-time state, yellow approval, per-session token, and reconnect claims. The UI may remain a non-functional design artifact only; it must not ship as a live monitor.
3. **Experimental app-server dependency:** No, if OpenAI provides a stable supported contract. An experimental-only method is not sufficient for the core release gate.
4. **Risk:** External roadmap/access dependency, unknown timing, possible privacy/approval fan-out constraints, and possible protocol churn.
5. **Recommended priority:** **1** — this is the only direction that can retain the full original core promise without lifecycle ownership.

### Priority 2 — Re-scope to a stable read-only snapshot/history monitor

1. **Preserve core experience:** Partially. It can still inspect existing Desktop Threads if `thread/list` / `thread/read` visibility is proved, but it becomes a delayed coarse status/history dashboard rather than a live event monitor.
2. **Functions to delete/change:** Delete live Item progress, authoritative Turn start/completion timing, yellow approval, per-session token updates, instant failure/interruption mapping, and strong missed-event recovery claims. Replace them with explicit “last refreshed / snapshot status / history may lag” semantics and bounded polling.
3. **Experimental app-server dependency:** **Yes under the currently tested local transport.** The methods are stable-schema reads, but the documented app-server/control transport maturity is still experimental/unsupported for production. This direction is not release-ready until the transport support boundary is accepted or stabilized.
4. **Risk:** Desktop Thread discovery is still unproved; persisted history can be lossy; polling can race active work; snapshot status may be stale; approval cannot be inferred; production transport support is weak.
5. **Recommended priority:** **2** — the least disruptive fallback, but it requires a new PRD and a new P0 focused on truthful snapshot semantics.

### Priority 3 — Convert Codex Monitor into a Monitor-owned Codex client

1. **Preserve core experience:** No. It can provide rich monitoring only for Threads started/resumed through Monitor; it does not monitor arbitrary existing Codex Desktop work.
2. **Functions to delete/change:** Replace “secondary observer of Desktop” with “alternate Codex client/launcher.” Task ownership, approvals, lifecycle controls, reconnect, and account behavior must be redesigned and disclosed. Existing Desktop-created Threads outside Monitor become unsupported.
3. **Experimental app-server dependency:** Likely yes for the rich client protocol as currently documented; a Codex SDK-based design may reduce transport exposure but still cannot observe existing Desktop sessions.
4. **Risk:** Largest product change, duplicated-client complexity, approval/safety ownership, user confusion, and dependence on experimental app-server behavior for deep integration.
5. **Recommended priority:** **3** — technically plausible only after explicit product reset; it abandons the defining experience.

## Final decision

**NO-GO.** The missing `thread/list` / `thread/read` reconciliation calls are a real test-coverage defect, but the stable schema contains no official purely observational subscription method for an existing Desktop Thread. The hard observer, correlation, approval, and reconnect gates remain unmet.

**不得进入 Phase 1。** Stop after Phase 0E; do not begin refactoring or architecture implementation without a separately approved redesign phase.
